## 1. 起始：从 macOS 版移植到第一个可运行包

### 1.1 项目定位与取舍

- 来源：macOS 版 momoのfish（`../qingdeng`，SwiftUI）的安卓移植，**Kotlin + Compose**，
  自用为主，不打算上架（README 开头）。
- 第一个提交是 2026-10-15 `cd392b6 移植：macOS 版 momoのfish 的安卓实现（Kotlin + Compose）`
  （103 个文件 / +18,836 行，一次性带入全模块骨架）；到 10-30 的 1.0.12，15 天共 80 个提交。
- 版本从起步的 0.1.0（versionCode 1）到 10-22 拉直为正式版 1.0.0，之后 8 天连发 12 个版本到 1.0.12。
- 砍掉的东西：mac 版依赖局域网 `FanqieCore` 的番茄在线源/榜单整块去掉，改为
  「跨书源搜索 + 书源管理 + 内置社区书源」；短剧/漫剧的 Go 服务端以二进制内置进 apk。
- 保留并重做的：Legado 书源规则引擎、TXT/EPUB 导入、三模式阅读器、听书、漫画竖读、
  整本缓存与导出。

### 1.2 起步顺序（10-15 ~ 10-16）

1. 建工程：Kotlin + Compose + Room + OkHttp + Coil + media3，`compileSdk 36 / minSdk 26 / targetSdk 35`。
2. 先按 mac 版起五个 tab：书架 / 书城 / 听书 / 短剧 / 我的；10-16 `e51d3db` 去掉独立阅读 tab，
   收敛成四个一级入口（v3 重设计后命名「书架 / 发现 / 短剧 / 我的」；读和听都从书架进）。
3. 按设计规范整体重做界面（10-16 `da011aa 界面：按设计规范整体重做（令牌层 / 组件四态 / 五个 Tab）`），
   设计依据是 [docs/design-system-v2.md](design-system-v2.md)。
4. 用真实资产验证主链路：内置社区书源首次启动灌库（`dafc933`）、短剧库二进制能起进程出推荐。
5. 用「真实参考图 + 截图」迭代界面，而不是只凭代码想象（书架宫格、阅读器、短剧页都是照参考图重做的）。

### 1.3 环境前置与最小可跑

```bash
# 前置：JDK 17、Android SDK（compileSdk 36）、NDK（只编短剧库用）、Go 1.24+
echo "sdk.dir=$HOME/Library/Android/sdk" > local.properties   # 该文件 gitignore

bash Tools/build-juku-android.sh     # 可选：把短剧库编成 libjuku.so（1.0.12 基线；正迁移中，见 §9）
./gradlew :app:assembleDebug
```

**不做 juku 那一步也能编过**，短剧页会显示「内置的短剧库缺失」，其余功能不受影响。
签名是自用钥匙 [keystore/momofish.jks](../keystore/momofish.jks)（已入库，release 构建直接使用），
这是后续「应用内覆盖升级」能成立的前提。

### 1.4 起始阶段就踩定的硬约束

| 约束 | 原因 | 证据 |
|---|---|---|
| 只打 `arm64-v8a` | 内置短剧库只编了这一份 | `app/build.gradle.kts` 的 `abiFilters` |
| 短剧库必须 cgo + NDK clang | 纯 Go 的 DNS 读不到 `/etc/resolv.conf`，联网全失败 | `Tools/build-juku-android.sh` 注释（1.0.12 基线） |
| 二进制要叫 `libjuku.so` 并开 `useLegacyPackaging` | Android 10 起私有目录禁止 exec，只能从 `nativeLibraryDir` 起 | README「编短剧库的两个坑」 |
| 书源 assets 存 `.gz`、运行时读明文名 | aapt 打包会自动解 gz 去扩展名 | README 内置书源一节 |

## 2. 开发：一轮改动的标准循环

### 2.1 需求从哪来

1. **用户直接要求**（聊天里的功能点、验收反馈、截图批注）——优先级最高，与设计图冲突时以用户为准
   （例：书架状态标签按真机反馈改成 14sp、等宽底色）。
2. **设计稿编号**（M01 组件母版 / P01–P30 业务页 / B01–B24 浮层组件 / S01–S14 状态 / D01–D08 深色），
   一一对应 [designed.md](../designed.md)。
3. **真机/模拟器截图发现**的问题（溢出、裁切、遮挡、大字号换行）。
4. **自检/探针失败**（`SelfCheckTest`、`VeneraProbeTest`、导出用例）。

### 2.2 先写 Agent Note 定方案（非平凡改动）

`.agents/notes/` 是项目的决策账本，当前 46 篇（2026-10-30 统计）：

| 状态 / 分类 | 数量 | 用途 |
|---|---|---|
| `proposed/feature` | 2 | 方案未定的提案（含验收标准与风险） |
| `proposed/architecture` | 1 | 架构级替换提案（短剧核心迁移） |
| `implemented/feature` | 9 | 已落地的新功能 |
| `implemented/bug-fix` | 18 | 缺陷根因与修复 |
| `implemented/simplification` | 5 | 主动做减法（删冗余 UI） |
| `implemented/process` | 8 | 发版、生图等流程记录 |
| `implemented/testing` | 2 | 验证轮次记录 |
| `archived/bug-fix` | 1 | 被后续方案取代 |

- 命名：`YYYY-MM-DD-主题.md`；标题后空一行，再写 `Status: proposed / implemented`。
  归档保留 `Status: implemented`、加 `Archived: YYYY-MM-DD` 并移到 `archived/<分类>/`；
  否决提案移到 `rejected/<分类>/`，使用 `Status: rejected — 原因`，保留提案形态。
- 模板（从 46 篇归纳，基本固定五节）：
  `Problem → Decision(或 Proposal) → Alternatives considered → Validation(或 Verification) → Consequences`；
  proposed 阶段用 `Proposal / Acceptance criteria / Risks`，并在评审后补「当前评审交付」。
  归档版把 `Validation` 写成 `Verification` 也可以——关键是**留下验证了什么、没验证什么**。
  当前模板固化在 `docs/ai-workflow.md` §17.2，结构和状态由 `scripts/check-workflow.py` 校验；接手时采用仓库模板。
- 什么时候写：涉及交互/数据契约/取舍/发版的决定都写；纯视觉微调写成一条短 note 也可，
  但「一次性临时改动」不写（AGENTS.md 也不给它补测试）。
- 与代码的关系：**note 状态跟实现进度走，不必等提交**。例如
  [2026-10-30-json-booklist-import.md](../.agents/notes/implemented/feature/2026-10-30-json-booklist-import.md)
  已从 `proposed` 移到 `implemented/feature/`，对应代码当时还在工作区未提交；
  反过来，proposed note 也可以先于任何代码存在。发版计划同样走这条路（1.0.7/1.0.8/1.0.10 的
  process 笔记先以 proposed 提交，上线后才改 implemented）。
- 移动方式是**删除旧文件 + 新增新文件**（git 历史里没有 rename 记录），状态行与
  `## Proposal → ## Decision` 要同步改；归档则移到 `archived/<分类>/`、保留 `Status: implemented`、
  加一行 `Archived: YYYY-MM-DD` 并**修好所有入链**。历史引用维护追加说明，原验证事实保留。

### 2.3 设计先行（界面改动）

- 设计走「先评审、后生成、再实现」：[design.md](../design.md) 只做索引，
  [designed.md](../designed.md) 是唯一方案源；v3 全量 77 张设计图（M01 母版 + P 页 30 + B 浮层 24 +
  S 状态 14 + D 深色 8）。**设计图本身不进 git**（在 gitignore 的 `output/uiux-v3/`），
  仓库里留的是规范文字；图库 `gallery.html`、逐页修正 `qa/pending-revisions.md` 只在本机工作区。
- 设计令牌落到代码：纸白 + 墨绿、24/20/18/16/14/12 字阶、16 卡片圆角、10 筛选圆角、24 浮层圆角；
  共享组件统一「空 / 加载 / 失败 / 有内容」四态。
- 实现按页面编号推进，每页用真实组件 + 隔离数据截图核对；设计图不能证明交互，
  可点的状态要另加回调断言。

### 2.4 编码约定

- 注释、文档一律中文；新能力优先复用既有的 `OnlineSource` / `LibraryRepository` / `ChapterLoader` 契约。
- 模块边界：`ui → data → core`；`source/legado`、`source/venera`、`playlet`、`tts` 各自独立；
  详见 README「模块地图」。
- 不轻易引第三方库：EPUB 导出是手写 zip，分页是按行累加自己算的，短剧库是内置二进制。
- Room 改表必须写迁移，schema 由 KSP 输出到 `app/schemas/` 并作为 androidTest 资产。

### 2.5 编译门槛

```bash
./gradlew :app:compileDebugKotlin            # 改完 Kotlin 的最低门槛
./gradlew :app:compileDebugKotlin :app:assembleRelease --console=plain   # 发版构建
```

**编译通过只说编译通过**（AGENTS.md）：不等于验证通过，别在总结里包装。

### 2.6 提交：Conventional Commits，一行标题

- 格式 `<type>: <说明>`，冒号后一个半角空格，说明中英文皆可，结尾不加句号，标题 ≤ 72 字符；
  需要展开时空一行，正文用 `-` 列点。类型表见 AGENTS.md（feat/fix/refactor/perf/docs/style/test/build/chore）。
- 配置了 `git config commit.template .gitmessage`，提交时会带格式提示。
- 实际分布（80 个提交）：feat 31、fix 10、build 10、refactor 8、docs 8、test 5、chore 3、perf 1，
  另有 4 个早期中文前缀提交（`移植：`/`界面：`/`短剧：`）——规范是 10-16 才引入的。
- 一个提交做一件事；**测试可以单独 `test:` 提交**（如 `8d7853a test: 阅读页顶栏显示书名的用例`）；
  一个版本通常拆成「feat/fix 实现 + build/chore 发布 + docs 记录」三类提交。
- 需要展开的提交确实写正文（`- ` 列点说明改了什么、为什么），发版记录会引用构建源码提交哈希。

### 2.7 收尾

- note 状态改 `implemented` 并移到对应分类；证据进 `docs/ux-evidence/<日期>-<主题>/`；
  README/AGENTS 里过时的说明同步改（数字、命令、限制）。
- 工作区状态要可解释：发版前确认没有混入无关的未提交改动。

## 3. 修改（bug 修复）：六步

1. **复现**：真机 / 模拟器 / 原始日志 / 录屏 / 受控数据。设备端优先用深链 + `am instrument`
   直达现场（见 §5.2），因为这台机器的 MIUI 禁了 `adb shell input`。
2. **定位根因**：先解释现象为什么发生，再改；必要时对照 Legado 源码或上游实现
   （规则引擎的多轮对齐就是这么做的）。
3. **补定向测试**：能断言的先写断言（数据层/排序/迁移），纯视觉的用截图回答。
4. **最小修复**：不夹带无关重构；行为变化拆出单独提交/单独 note。
5. **取证**：截图、instrument 原始输出、logcat；失败和宿主缺失的记录也保留，不粉饰。
6. **写 bug-fix note**（Problem/Decision/Alternatives/Validation/Consequences）并提交。

修复准则（来自已有笔记）：

- **不要靠文案猜状态**：网络问题用显式 `BookCacheState.waitingForNetwork` 和
  `cacheTask = waiting_network`，不解析本地化错误文案。
- **保持旧数据契约**：旧 `incomplete` 记录不强行迁移，重试时按实际原因重新分类。
- **用户反馈优先于设计图**：例如书架标签 14sp/等宽底色、书名居中，按用户真机意见覆盖设计示例。
- **只跑受影响的用例**，不因为一个小修跑整套无关回归（AGENTS.md「别跑没用的测试」）。

五个典型根因（README「踩出来的坑」完整版，都留在代码注释里）：

| 现象 | 根因 | 修法 |
|---|---|---|
| 服务端回了 153KB，客户端拿到 0 字节 | `withContext(IO)` 返回后切回主线程再读 `body.string()`，抛异常被 `runCatching` 吞成空串 | 整个 `send()` 含读 body 放 IO；空 body 当可重试错误 |
| 重启后短剧列表/搜索回 200 + 空 body | GET 没走站源握手；身份按含随机端口的完整 URL 存，重启失配 | GET 也握手；身份按 host 存 |
| 点听书又立刻关掉 → 进程被杀 | 前台服务必须 5 秒内 `startForeground()`，启动被 stop 抢先 | `onCreate` 即进前台；停止改发 `ACTION_STOP` |
| 正文第一行被顶栏压住 | `Scaffold` 已消费 insets，读 `statusBars` 得 0 | 实测顶栏/底栏高度再传给阅读器，分页与渲染同一份 |
| 短剧库某些接口 200 + 空 body | 服务端 `writeJSON` 吞编码错误 | 打补丁先 Marshal 到内存，失败回 502 带原因 |

## 4. 优化：性能 / 重构 / 做减法 / 界面收口

### 4.1 性能（`perf:`）

套路固定：**先证明瓶颈在主线程或慢链路 → 移位 IO / 加超时 / 加缓存 / 限数量 → 失败时保留旧内容**。
代表提交 `d7635c5 perf: 书城漫画推荐位移出主线程并加缓存`：

- 发现页 JS 初始化与网络改到 `Dispatchers.IO`，切漫画 tab 不再卡主线程；
- 单源 10 秒超时，坏源不拖住整个推荐位；成功源回写 `lastSuccessAt`，下次优先问；
- 推荐结果落盘缓存 7 天：冷启动先上上次的榜，网络回来再替换；
- 首页榜单最多 30 本，减少封面解码与列表长度；取榜失败不清空已有内容。

能算出数的要给出数：缓存导出单本 999 章 / 6.4MB 正文，真机 TXT 约 1.8 秒、EPUB 约 1.7 秒。
性能提交不配「冒烟测试」，用可观察行为（切 tab 不卡、坏源不影响其他源）和截图/日志说明。

### 4.2 重构（`refactor:`，不改行为）

- 对齐上游语义：规则求值改成 Legado 的 `SourceRule` 管道、JS 绑定按 Legado 语义对齐、
  规则预处理复刻 Legado——分多次 refactor 提交，每次保持可编译、现有用例可过。
- 收口重复结构：组件「空/加载/失败」三态收口、在线详情与短剧卡收口（`5d724d0`、`a0843a4`）。
- **重构不改行为**：真要改行为就拆成 feat/fix；重构提交的说明里写清边界。

### 4.3 做减法（`simplification`）

主动删冗余 UI，每项一篇 note + 前后对照截图，同时写清「不这么做会怎样」的备选：

- 底部导航激活态去掉下划线、我的页去掉标题副标题、阅读页去掉常驻页脚信息、
  小说下载范围/预下载数量改成文字选项按钮、升级卡片重排信息层级。
- 减法同样以用户反馈为最高优先级；设计图没覆盖的取舍，在 note 的
  `Alternatives considered` 里交代。

### 4.4 界面收口（设计 vs 实际）

- 逐页对照设计编号：先拍实际截图，再和 designed.md 该页并排看，列出偏差 → 修正 → 复拍。
- 77 项清单里有 17 项先有真机截图、其余 60 项后来补；最终交付 76 个运行页面/状态的
  模拟器验收图库（[docs/ux-evidence/2026-10-27-emulator-acceptance/index.html](ux-evidence/2026-10-27-emulator-acceptance/index.html)）。
- 覆盖表要区分：本轮截图 / 交互断言 / 外部服务未覆盖，避免把「编译过」当「整页验收」。

### 5.3 选择原则（AGENTS.md）

- 改完 Kotlin 先 `:app:compileDebugKotlin`；库/引擎类纯逻辑跑设备自检；界面改动用截图；
  需要点击才能看到的中间状态，临时把状态强制成那个值截一张，**看完立刻改回去**。
- 不写、不跑没有断言价值的「冒烟测试」：装完包 `am start` 看一眼没崩、为了确认能跑重复跑已有测试、
  给一次性临时改动补测试、与改动无关的回归重跑——都不算验证。
- 一次改动只跑受影响用例；失败日志保留，不重跑凑绿。

### 5.4 当前测试缺口（别假装没有）

- **没有 CI**：所有构建/测试/发版都是本机手工执行，靠脚本和记录保证可复现。
- README「自检」里的 `UiWalkthroughTest` 已被 `*FullUiAuditTest` 系列取代，命令是旧的；
  截图默认落在 app 私有 `files/ux-reliability/`，不是 README 写的 `files/shots`。
- `scripts/run-ui-audit.py`、`scripts/build-emulator-acceptance.py` 没有被 README/AGENTS 引用，
  后者路径写死某一轮证据目录，不能直接复用。
- 公网书源、WebDAV、在线 TTS 依赖网络环境，不能作为稳定断言；Venera 探针在真机上通常要
  `adb reverse tcp:7897 tcp:7897` 借本机代理。
- 单测只覆盖纯逻辑，UI 主要靠截屏 + 回调查断言，不做像素级对比。

### 6.1 证据放哪、长什么样

界面/功能验证的证据统一进 `docs/ux-evidence/<日期>-<主题>/`（当前 30 个目录、24 份 README、

- M/L 使用完整模板；S 级纯视觉/文案可用 `docs/ai-workflow.md` §17.4 三段精简模板，保留环境与产物、核对与原始输出、复跑、失败及未验证范围。
- 失败记录保留（例如「测试宿主缺失」的 result.txt 明确写「不计为通过」），不把旧图/new build
  混用；重拍要说明本轮构建时间。截图存设备原始分辨率、不裁剪（局部图只裁底部且不修图）。

### 6.2 真机 vs 模拟器

- 真机：小米 12S（`22081212C`，序列号 `d3ed3c68`，Android 15，1220×2712），MIUI 禁点击注入，
  所以主要靠深链 + `am instrument`；纯视觉核对用 `adb exec-out screencap -p`。
- 模拟器：`emulator-5554`（Android 16，1080×2400），用于 76 项验收、360dp、1.3 倍字号、
  深浅色和动效帧核对。
- 改过系统字体/密度/主题/开关的，验证完要恢复并记录（app-color-themes 的 note 明确写了恢复原值）。

### 6.3 隔离数据，不碰用户数据

测试用内存 Room + 随机命名 preferences + 受控媒体资产（`reading-resume.mp4` 等），

### 6.4 截图标准

- 截图必须**能直接回答问题**：布局对不对、有没有裁切、字号/间距/颜色是否按设计。

### 6.5 发布验证（线上核对）

发布后的核对不是「部署成功」，而是**下载回来再核对一遍**（1.0.12 样板，14 项）：

| 包名/版本 | `com.lizhiwei.momofish` / 1.0.12（10012） |

## 7. 发布：从版本号到线上

### 7.1 版本号规则

`versionCode = 主版本 × 10000 + 次版本 × 100 + 修订`（1.0.12 → 10012）。客户端只按
`versionCode` 比大小，所以**必须单调递增**；从 0.1.0（1）到 1.0.0（10000）是一次性拉直，
之后每个补丁版 +1（1.0.1→10001 … 1.0.12→10012）。

### 7.2 发布前检查

1. 工作区干净、`origin/main` 无分叉；本批验证已完成并留证据（不重复跑无关测试）。
2. 资产有变才重跑对应管线（短剧库 / 书源 / Venera / 品牌资产，见 §8.2）。
3. 改 `app/build.gradle.kts` 的 `versionCode` / `versionName`。
4. 改 `vercel/update/api/latest.js` 的 `changelog` / `force`（脚本不动这两项）。

### 7.3 构建并留原始输出

```bash
./gradlew :app:compileDebugKotlin :app:assembleRelease --console=plain 2>&1 \
  | tee docs/releases/<ver>-build.txt
```

### 7.4 `vercel/update/deploy.sh` 做了什么

1. 除非 `--no-build`，先 `./gradlew :app:assembleRelease`；
2. 把 APK 复制到 `vercel/update/public/app-release.apk`；
3. 从 `build.gradle.kts` 读 versionCode / versionName；
4. 算 SHA-256 和字节数，用内联 node 脚本写回 `api/latest.js`（`apkUrl` / `sha256` / 版本）；
5. `vercel link` 到既有项目 `momofish-update`（`deploy` 不接受 `--project`）；
6. `vercel deploy --prod`；
7. 自检：`curl /api/latest` 和 APK 直链 HEAD（**只验可达，不比对 sha256**，完整核对靠人工）。

`--no-build` 用于「包已核对、只补部署/换元数据」；1.0.12 就是这么发的。

### 7.5 双通道与标签

- **主通道**：Vercel 更新站（App 内「检查更新」走 `https://update.leempty.site/api/latest`）。
- 启动提醒门槛由可选 `minRecommendedVersionCode` 控制，发布者按关键修复范围维护；部署脚本保留此字段。客户端的检查间隔、忽略和冷却规则见 [更新接口说明](../vercel/update/README.md#启动更新提醒)。
- **镜像/发布页**：GitHub Release，标签 `v<版本>` 指向**实际构建源码提交**，上传同一 APK。
- 发布记录/元数据的后续提交**不移动标签**；GitHub Release 目前是人工步骤（仓库无 `gh` 脚本）。

### 7.6 发布记录七件套（`docs/releases/`）

| 文件 | 内容 | 从哪版开始 |
|---|---|---|
| `<ver>.md` | 发布记录正文：更新内容 / 构建与包核对 / 发布位置与线上核对 / 验证范围 | 1.0.7 |
| `<ver>-package.json` | 本地包核对数据（包名/版本/签名/字节/SHA/内容抽查/源码提交） | 1.0.7 |
| `<ver>-online.json` | 线上完整下载核对数据 | 1.0.7 |
| `<ver>-build.txt` | gradle 构建原始输出 | 1.0.10 |
| `<ver>-deploy.txt` | `deploy.sh` 部署原始输出 + curl 自检 | 1.0.10 |
| `<ver>-github.json` | GitHub Release 核对 | 1.0.12 |
| `<ver>-latest.json` | 部署后接口返回快照 | 1.0.12 |

> `deploy.sh` 只负责写 `api/latest.js` + 部署 + curl 自检；`docs/releases/` 里的记录全是人工整理的
> （终端输出 tee 成 txt、核对数据写成 json），脚本不生成。

### 7.7 发布坑位

- 国内直连 `*.vercel.app` 会超时，必须用自有域名；Cloudflare 记录保持**仅 DNS**（开橙云 525）。
- **不要用 Serverless Function 转发 APK**（响应上限 4.5MB，包 28MB+），放 `public/` 静态文件。
- 签名必须一直是同一把 keystore，否则装不上/无法覆盖升级；`apkUrl` 必须能直接拿到 APK。
- 接口有约 1 分钟 CDN 缓存，发版后别过早下「没生效」的结论。
- 本地 `output/` 产物命名（手工，非脚本）：`momofish-<ver>.apk`、`momofish-<ver>-online.apk`、
  `momofish-<ver>-package.json`、`momofish-<ver>-release-notes.md`；`output/` 整体 gitignore。

## 8. 资产、文档与协作约定

### 8.1 工作流是逐步长出来的

### 8.3 文档与证据的写法

- 相对链接引用仓库内文件；日期用 `YYYY-MM-DD`；版本记录写「源码提交 + 字节 + SHA-256 + 签名」。
- Agent Note 的当前模板、状态和分类规则以 `docs/ai-workflow.md` 为准，仓库自检脚本为 `scripts/check-workflow.py`；换机器/换人不依赖作者本机技能目录。
- 笔记里「未验证」必须明说；不要把「编译过」写成「验证通过」。
- 改动后同步更新 README 的过时数字/命令；当前已知文档漂移见 §9。

### 8.4 提交与发版的配对

- 功能/修复 + 版本号提升 → `feat:`/`fix:`
- 发布配置/接口元数据 → `build:`/`chore:`
- 发布记录与线上核对 → `docs:`
- 测试单独补 → `test:`；规则引擎/结构收口 → `refactor:`

## 10. 一页纸清单

**开始一轮改动**

1. 明确需求来源（用户 / 设计编号 / 截图问题 / 探针失败）。
2. 非平凡改动先写 `proposed` note（Problem / Proposal / Alternatives / Acceptance / Risks）。
3. 界面改动先查 designed.md 对应页与令牌。
4. 改代码 → `:app:compileDebugKotlin`。
5. 补定向测试/截图；只跑受影响用例。
6. note 转 `implemented`，证据进 `docs/ux-evidence/`。
7. 按 Conventional Commits 提交（一提交一件事，必要时拆 `test:`）。

**修一个 bug**

1. 复现（深链/隔离数据/日志）→ 2. 根因 → 3. 定向测试 → 4. 最小修复 →
5. 截图或断言取证（失败也留）→ 6. `implemented/bug-fix` note → 7. 提交。

**发一版**

1. 工作区干净、验证已完成 → 2. 改 versionCode/Name + latest.js changelog →
3. `compileDebugKotlin assembleRelease` 并 tee build.txt → 4. 本地包核对 →
5. `./vercel/update/deploy.sh [--no-build]` → 6. 等 1 分钟缓存，完整下载核对 →
7. GitHub Release（人工，标签指构建源码）→ 8. 写 `docs/releases/<ver>.md` 与 json →
9. `docs:`/`build:` 提交推送，**标签不移动**。

**交付验收**

1. 证据目录有 README + 原始输出 + 能回答问题的截图；
2. 区分「截图证明 / 断言证明 / 未验证」；
3. 设计编号可回溯（Pxx/Bxx/Sxx/Dxx）；
4. 设备、构建 SHA、时间可追溯。
