## 技术栈示例

- Android Kotlin：静态编译可用 `./gradlew :app:compileDebugKotlin`；JVM 定向测试可用 `./gradlew :app:testDebugUnitTest --tests <完整类名>`。设备命令必须按本项目包名、测试宿主和已安装测试包填写。
- Flutter：纯 UI 间距、字号、颜色、文案、对齐微调只跑 `fvm dart format <改动文件>` 与 `fvm flutter analyze --no-pub`；同批修改完成后热更新到模拟器，核对最终画面一次。视觉疑点、差异比较或明确要求时才截图/量像素；涉及行为、契约、数据流、路由、状态机或测试文件时跑相关 `fvm flutter test <测试文件>`，不能用截图替代断言。
- Web/其他：采用项目现有类型检查、lint、单元/集成/端到端工具；不为接入流程新增框架依赖。

## 一轮工作

定向读约定与影响面 → 按手册 §4.3 选路径并简述目标/验证 → 重要决定先写 proposed → 已有授权内实现 → 按 §8 做相关检查，满足停止条件就收尾 → 按 §9 精简或引用证据 → 有 Note 时改 implemented 并修链接 → 适用自检与简短交付。

风险、询问、验证和证据的边界统一采用执行手册 §4/§8/§9。文件数不决定流程重量，V 编号只作方法标签；本表仅填写项目实际命令与明确的特殊要求。

上游来源与安装基线见 `.agents/workflow/installation.json`；已接入后可直接要求 AI “update 工作流”。操作与旧版迁移见[安装与升级](distribution.md)。留痕规则随项目携带，不需要 Codex 全局技能。

## 自检与发布记录

`python3 scripts/check-workflow.py --strict --commits 0` 检查全量结构及本地链接。`--commits 0` 明确不读 Git；有历史且需要检查时用 `--commits 20`。脚本只读，不运行项目构建、设备操作、网络请求或发布。

空项目允许没有发布记录。开始写版本记录后，默认每版用 `<版本>.md`、`<版本>-build.txt`、`<版本>-package.json`、`<版本>-online.json`。package 是本地产物核对，online 是发布后核对；它们可适用于安装包、网站部署或其他产物，字段见 [发布模板](../templates/release.md)。仅本地试用不造发布记录。不同项目可修改 `release_required` / `release_optional`。

## 已知边界

模板未填写时不能宣称项目构建或测试通过。自检不能验证 Markdown 锚点、截图内容、断言质量或产物摘要；原版 Android 项目和工具仅保存在 [来源参考](../reference/README.md)，不会自动安装到试用项目。
