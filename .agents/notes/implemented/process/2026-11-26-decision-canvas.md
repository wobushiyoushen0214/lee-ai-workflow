# Agent Note: 将决策画布作为可选工作流组件

Status: implemented

## Problem

用户已要求独立的决策画布，随后希望结合 lee-ai-workflow 使用。画布读取工作流的 Markdown 决策、证据与发布目录；若源码与工作流入口分散，后续安装与更新容易遗漏。原 dsh-decision-canvas 插件需要保持原样。

## Decision

在本仓 `plugins/decision-canvas` 维护独立的 Agent 通用版源码、Skill 与已构建运行包，通过仓库 marketplace 分发。项目 AGENTS 模板和执行手册增加按需入口，使用文档放在已有受管理的 docs/distribution.md 中，不把 Node、插件运行包或额外技能安装进每个业务项目。

用户要求打开画布时，Agent 通过 MCP 登记当前项目、取得本地 URL；Codex 在右侧浏览器面板展示，其他宿主可打开本地网页。检索、拖动、筛选、正文和周期刷新由本地代码执行；只有明确的 Agent 分析才进入模型上下文。分析使用当前 Agent 对话、冻结来源并检查版本，保留原 proposed/implemented/rejected/archived 与 Markdown/Git 契约。

## Alternatives considered

- 在 Python 安装器中启动系统弹窗：跨平台和无图形环境不一致，且安装器不拥有 Agent 交互；选择框由 AI 宿主的可用交互工具展示。已有选择和普通更新跳过。
- 将产品命名绑定 Codex：工作流服务多个 Agent，标准 MCP 可复用；采用“决策画布”，保留 Codex 专属右侧展示适配。

- 新增固定分发文件：旧版安装器的固定文件列表不会发现新路径，可能先更新入口却漏掉文档；复用已有 docs/distribution.md，使 1.4.0 安装器也能完整升级。

- 将 Node 和画布作为基础安装前提：会破坏纯 Python、无第三方依赖的工作流基础路径，因此保持可选。
- 每个业务项目复制完整画布：扩大更新面，且没有必要；使用一次安装的 Codex 插件服务多个项目。
- 自动在每次开发任务前打开画布或调用分析：会增加上下文与操作成本；按任务需要检索，用户要求可视化时才打开。
- 修改原 Harness 插件：不符合用户保留原插件的要求，使用独立 Codex 实现。
- 工作流只放外部插件链接：本地没有独立公开插件仓库，缺少可一起审阅的维护入口；源码与可安装产物放在本仓的可选组件目录。

## Validation

基础工作流 55 项回归通过；实际用 Git HEAD 中的 1.4.0 安装器创建临时项目，再由该项目自带旧命令升级到本地 1.5.0，入口与画布说明完整到达、strict 检查通过，项目中没有插件或 Node 依赖。画布完成 40 项行为测试、真实 MCP 安装与浏览器交互检查。原始输出和范围见 [本次证据](../../../../docs/ux-evidence/2026-11-26-decision-canvas/README.md)。

## Consequences

工作流与可选画布有共同维护入口，多个项目共享一次插件安装；基础 Python 使用方式与业务项目内容保持。代价是维护随插件分发的 Node/浏览器构建产物，并分别管理工作流和插件更新。打开页面与本地交互不持续调用模型，历史分析仍消耗当前 Agent 对话的输入输出 token。

## Risks

已构建浏览器和 MCP 需要随源码更新，插件运行需要 Node 22.19+。本次接入在本地完成，GitHub 远端只有发布之后才包含该组件。未加载 MCP 的已有聊天可通过随包 CLI 打开页面；新聊天优先使用插件工具。独立画布的来源代码归属和许可证需要随包保留。

## 安装选择

用户进一步要求通过 AI 首次安装工作流时显示是否安装插件的选择框。使用宿主可用的交互选择工具，已有明确选择时直接执行；普通更新不再询问。选择等待期间可继续基础安装，未选择不安装可选插件。

## 通用命名与协议

产品统一称为“决策画布”，插件 ID 与目录为 decision-canvas；Codex 的右侧打开方式作为宿主适配。其他 Agent 通过标准 stdio MCP 接入，分析在当前 Agent 会话中执行。为保留本轮已有分析，继续读取早期 codex-conversation / awaiting_codex 记录，新记录使用 agent-conversation / awaiting_agent。
